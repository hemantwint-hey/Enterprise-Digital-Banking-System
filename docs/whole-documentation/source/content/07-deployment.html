2. Running Locally (today)

2.1 Prerequisites

  • JDK 17+, Git, Docker Desktop (for Kafka), MySQL 8 running on localhost:3306.
  • Sibling repository notification-service (optional, for notifications).

2.2 Steps

# 1. Kafka (single-node KRaft) - compose file lives in notification-service
cd ../notification-service && docker compose up -d && docker ps      # notification-kafka is Up

# 2. Environment (PowerShell)

$env:JWT_SECRET="at-least-32-random-bytes-base64-encoded-secret-value"

# 3. banking-app (port 8080) - creates banking_db automatically
cd ../Enterprise-Digital-Banking-System
./mvnw spring-boot:run

# 4. notification-service (port 8081) - in another terminal
cd ../notification-service && ./mvnw spring-boot:run

6. AWS Deployment PLANNED

  1. Build: ./mvnw clean package -DskipTests → target/Enterprise-Digital-Banking-System-0.0.1-SNAPSHOT.jar.
  2. Create an RDS MySQL 8 instance (private subnet, security group allowing 3306 only from the EB instances).
  3. Create an Elastic Beanstalk Java (Corretto 17) application; upload the jar (console or eb init / eb create).
  4. Configuration → Software → Environment properties: SPRING_PROFILES_ACTIVE=prod, DB_PASSWORD, JWT_SECRET, SPRING_DATASOURCE_URL=jdbc:mysql://<rds-endpoint>:3306/banking_db, SERVER_PORT=5000 (EB’s default proxy port).
  5. Attach an ACM certificate to the load balancer for HTTPS.
  6. Kafka (MSK) and Redis (ElastiCache) are deferred: they stay containerised and documented. Without a broker, producers log errors and transfers still succeed.
  7. Verify: curl https://<eb-url>/actuator/health → {"status":"UP"}.

7.2 Logging rules

LevelUse for
ERRORUnexpected failures needing action (Kafka publish failed, unhandled exception)
WARNRecoverable problems (rate limiter unavailable → fail-open, retries)
INFOBusiness milestones (transfer completed with reference, loan approved) — no PII
DEBUGDiagnostics, SQL (dev only)

Never log passwords, JWTs, full Aadhaar/PAN, or request bodies of auth endpoints. Log the transaction reference, not the account holder’s details. Logs are distinct from the audit trail: logs are for operators and may be rotated; audit_logs is a compliance record.

9. Backup and Recovery

ItemApproach
ObjectivesRPO ≤ 15 min (max data loss), RTO ≤ 1 h (max downtime)
Local / ComposeNightly logical dump: docker exec mysql mysqldump -uroot -p$DB_PASSWORD --single-transaction --routines banking_db | gzip > backup/banking_$(date +%F).sql.gz; keep 14 days
AWS RDSAutomated backups (7–35 days) + point-in-time recovery from binlogs; manual snapshot before every release
SchemaRecreated from Flyway migrations in git
KafkaNot a system of record. Events lost before consumption only cost a notification; source of truth is MySQL
RedisCache only — no backup needed; flushed on restore
SecretsStored in EB / Secrets Manager, not in backups

9.1 Restore procedure

  1. Stop banking-app (prevent writes).
  2. Restore: gunzip -c banking_YYYY-MM-DD.sql.gz | mysql -uroot -p banking_db (RDS: restore snapshot / PITR to a new instance and switch the URL).
  3. Start the app; Flyway validates the schema version.
  4. Flush Redis (redis-cli FLUSHALL) so no pre-restore balances are served.
  5. Reconcile: for every account, balance must equal the last ledger_entries.balance_after_entry.
  6. Test the restore quarterly — an untested backup is not a backup.
-- Reconciliation query
SELECT a.id, a.account_number, a.balance, le.balance_after_entry
FROM accounts a
JOIN ledger_entries le ON le.id = (SELECT MAX(id) FROM ledger_entries WHERE account_id = a.id)
WHERE a.balance <> le.balance_after_entry;    -- must return 0 rows
