2. Sequence Diagrams — Authentication

2.1 Register

sequenceDiagram
  actor C as Client
  participant AC as AuthController
  participant US as UserServiceImpl
  participant UR as UserRepository
  participant PE as BCryptPasswordEncoder
  participant AS as AuditService
  C->>AC: POST /auth/register {fullName, username, email, phone, password, confirmPassword}
  AC->>AC: @Valid (sizes, email format, phone regex)
  alt validation fails
    AC-->>C: 400 ErrorResponse "field: message"
  end
  AC->>US: register(request)
  US->>UR: existsByEmail(email)
  alt e-mail taken
    US-->>C: 409 "Email already exists"
  end
  US->>US: password equals confirmPassword?
  alt mismatch
    US-->>C: 401 "Password do not match"
  end
  US->>PE: encode(password)
  US->>UR: save(User role=CUSTOMER, status=ACTIVE)
  US->>AS: log(CREATE, "User", userId, "User registered")
  US-->>AC: RegisterResponse(success=true)
  AC-->>C: 201 Created
Figure 4 — Register

2.2 Login

sequenceDiagram
  actor C as Client
  participant AC as AuthController
  participant US as UserServiceImpl
  participant UR as UserRepository
  participant PE as PasswordEncoder
  participant J as JwtUtil
  participant AS as AuditService
  C->>AC: POST /auth/login {email, password}
  AC->>US: login(request)
  US->>UR: findByEmail(email)
  alt user not found
    US->>AS: log(LOGIN_FAILED, "user not found")
    US-->>C: 404 "Invalid email id"
  end
  US->>PE: matches(raw, hash)
  alt wrong password
    US->>AS: log(LOGIN_FAILED, "invalid password")
    US-->>C: 401 "Password didnt match"
  end
  US->>J: generateToken(email)
  J-->>US: HS256 JWT (sub=email, exp=now+24h)
  US->>AS: log(LOGIN, "Login successful")
  US-->>C: 200 {success, message, token}
Figure 5 — Login

2.3 Authenticated request (JWT filter)

sequenceDiagram
  actor C as Client
  participant F as JwtAuthenticationFilter
  participant J as JwtUtil
  participant UDS as CustomUserDetailsService
  participant SC as SecurityContext
  participant EP as JwtAuthenticationEntryPoint
  participant CT as Controller
  C->>F: GET /api/v1/... Authorization: Bearer token
  alt header missing / not Bearer
    F->>CT: continue unauthenticated
    CT-->>EP: AuthenticationException
    EP-->>C: 401 "Authentication required..."
  else token present
    F->>J: extractEmail(token) (verifies signature)
    F->>UDS: loadUserByUsername(email)
    F->>J: validateToken(token, user) (subject match, not expired)
    F->>SC: setAuthentication(user, authorities=[ROLE])
    F->>CT: continue
    CT-->>C: 200 response
  end
  Note over F,EP: JwtException or unknown user: context cleared, entry point returns 401

3. Sequence Diagrams — Money Movement

3.1 Transfer (the core flow)

sequenceDiagram
  actor C as Client
  participant TC as TransactionController
  participant TS as TransactionServiceImpl
  participant AR as AccountRepository
  participant BR as BeneficiaryRepository
  participant TR as TransactionRepository
  participant LS as LedgerService
  participant EP as TransactionEventProducer
  participant AU as AuditService
  participant K as Kafka
  C->>TC: POST /api/v1/transactions/transfer
  TC->>TS: transfer(request)
  Note over TS: @Transactional begins
  TS->>AR: findById(sourceAccountId)
  alt beneficiaryId given
    TS->>BR: findById(beneficiaryId)
    TS->>TS: must be ACTIVE and owned by source customer
  else destinationAccountId given
    TS->>AR: findById(destinationAccountId)
  end
  TS->>TS: source != destination, both ACTIVE, balance >= amount
  TS->>AR: save(source balance - amount)
  TS->>AR: save(destination balance + amount)
  TS->>TR: save(Transaction TRANSFER, SUCCESS, TXN ref)
  TS->>LS: recordTransactionEntries(txn)
  LS->>LS: DEBIT source + CREDIT destination
  TS->>EP: publish(TransactionCompletedEvent)
  EP-)K: send("transaction.completed", key=accountId, json)
  TS->>AU: log(CREATE, "Transaction", "Transfer made")
  Note over TS: commit (all or nothing)
  TS-->>TC: TransactionResponse
  TC-->>C: 200 OK
Figure 7 — Transfer. Any exception before commit rolls back balances, transaction, ledger and audit rows.

3.2 Deposit and withdrawal

sequenceDiagram
  actor C as Client
  participant TS as TransactionServiceImpl
  participant AR as AccountRepository
  participant TR as TransactionRepository
  participant LS as LedgerService
  participant AU as AuditService
  C->>TS: deposit / withdraw {accountId, amount, remarks}
  TS->>AR: findById(accountId)
  TS->>TS: account ACTIVE?
  opt withdraw
    TS->>TS: balance >= amount? else 400 "insufficient balance"
  end
  TS->>AR: save(new balance)
  TS->>TR: save(DEPOSIT or WITHDRAWAL, SUCCESS)
  TS->>LS: recordTransactionEntries: CREDIT (deposit) / DEBIT (withdraw)
  TS->>AU: log(CREATE, "Deposit made" / "Withdrawal made")
  TS-->>C: TransactionResponse
Figure 8 — Deposit / withdrawal (no Kafka event today)

4. Sequence Diagrams — Beneficiary, Loan and EMI

4.1 Add and activate beneficiary → notification

sequenceDiagram
  actor C as Client
  participant BS as BeneficiaryServiceImpl
  participant DB as MySQL banking_db
  participant P as BeneficiaryEventProducer
  participant K as Kafka
  participant NC as BeneficiaryEventConsumer
  participant NSV as NotificationService
  participant NDB as notification_db
  participant SMTP as SMTP
  C->>BS: POST /beneficiaries {customerId, beneficiaryAccountId, nickName}
  BS->>DB: customer + account exist, not duplicate
  BS->>DB: save(status=PENDING) + audit CREATE
  BS-->>C: 201 BeneficiaryResponse(PENDING)
  C->>BS: PATCH /beneficiaries/{id}/activate
  BS->>DB: status PENDING -> ACTIVE + audit UPDATE
  BS->>P: publish(BeneficiaryActivatedEvent)
  P-)K: beneficiary.activated (key=customerId)
  BS-->>C: 200 BeneficiaryResponse(ACTIVE)
  K-)NC: poll (group notification-service)
  NC->>NSV: send(NotificationRequest EMAIL, MEDIUM, idempotencyKey=eventId)
  NSV->>NDB: insert (unique idempotency_key)
  NSV->>SMTP: deliver (retry with exponential back-off)
  NSV->>NDB: status SENT or FAILED
Figure 9 — Beneficiary lifecycle and asynchronous notification

4.2 Apply for and approve a loan

sequenceDiagram
  actor CU as Customer
  actor M as Manager
  participant LS as LoanServiceImpl
  participant DB as MySQL
  participant ES as EmiServiceImpl
  CU->>LS: POST /loans {customerId, disbursementAccountId, loanType, principal, rate, tenure}
  LS->>DB: customer + account exist
  LS->>LS: emi = P*r*(1+r)^n / ((1+r)^n - 1)
  LS->>DB: save(Loan PENDING, emiAmount)
  LS-->>CU: 201 LoanResponse(PENDING)
  M->>LS: PATCH /loans/{id}/approve
  LS->>LS: status must be PENDING
  LS->>DB: account.balance += principal (disbursement)
  LS->>DB: loan ACTIVE, approvedAt=now
  LS->>ES: generateSchedule(loan)
  loop installment 1..tenureMonths
    ES->>ES: dueDate = today + i months, amount = emiAmount
  end
  ES->>DB: saveAll(EMIs PENDING)
  LS-->>M: 200 LoanResponse(ACTIVE)
Figure 10 — Loan application and approval (reject: PENDING → REJECTED, nothing else)

4.3 Pay EMI

sequenceDiagram
  actor CU as Customer
  participant ES as EmiServiceImpl
  participant ER as EmiRepository
  participant LR as LoanRepository
  CU->>ES: PATCH /emis/{emiId}/pay
  ES->>ER: findById(emiId)
  alt already PAID
    ES-->>CU: 400 "EMI is already paid"
  end
  ES->>ER: save(status=PAID, paidAt=now)
  ES->>ER: existsByLoanIdAndStatusNot(loanId, PAID)
  alt no unpaid EMIs left
    ES->>LR: save(loan CLOSED, closedAt=now)
  end
  ES-->>CU: 200 EmiResponse
  Note over ES: PLANNED - debit EMI amount from account via TransactionService + ledger + audit

6.1 Transaction status

Transactions are written directly as SUCCESS inside the same database transaction that moves the money; a failure rolls everything back, so no FAILED row is stored today. PENDING (asynchronous / inter-bank payments), FAILED (persisted failures) and REVERSED (compensating transaction) are reserved for future use.
