1. System Overview

The Enterprise Digital Banking System is a backend platform that simulates the core operations of a retail bank: user registration and login, customer onboarding with KYC, savings/current accounts, deposits, withdrawals and transfers backed by a double-entry ledger, saved beneficiaries, loans with an EMI repayment schedule, and a full audit trail. Customer-facing notifications are handled by a separate notification-service that consumes domain events from Apache Kafka.

1.1 Goals

  • Correctness of money movement — every balance change is recorded atomically as a transaction plus ledger entries; debits always equal credits.
  • Security — stateless JWT authentication, BCrypt password hashing, no secrets in source control.
  • Traceability — every important state change is written to audit_logs with who, what, old/new value and client IP.
  • Loose coupling — notifications are asynchronous; a notification outage can never fail or slow a transfer.
  • Operability — containerised, observable (Actuator, Prometheus, Grafana) and deployable to AWS.

ControllerThin. Validates input with Bean Validation (@Valid), delegates to exactly one service call, never touches repositories, returns DTOs only (never entities).

5. Event-Driven Integration

<topic>.DLTDeadLetterPublishingRecovererConsumer failed 3 times (2 s apart)sameManual inspection PLANNED
  • Payloads are JSON strings (StringSerializer) built with Jackson. Keying by account / customer keeps all events for one account in order on one partition.
  • Publishing is fire-and-forget: producer exceptions are logged and swallowed so a Kafka outage never rolls back a committed money movement.
  • The event is published inside the service’s @Transactional method, before commit. GAP if the DB commit later fails, a notification can be sent for a transfer that did not happen. A transactional outbox (or @TransactionalEventListener(AFTER_COMMIT)) is the documented fix.

8. Architecture Decision Records

Each ADR records one significant decision: context, decision, and consequences. Status values: Accepted, Proposed, Superseded.

ADR-001 — Modular monolith, package-by-feature  Accepted

Context: one developer, many related banking domains that share transactions (a transfer touches accounts, ledger, audit).
Decision: a single Spring Boot app with one package per feature, each with controller/service/repository/entity sub-packages.
Consequences: simple local ACID transactions across modules; modules can later be extracted along the same seams. Discipline needed to avoid cross-module cycles.

ADR-002 — Notifications in a separate service via Kafka  Accepted

Context: sending e-mail is slow and unreliable; a failed e-mail must never fail a transfer.
Decision: remove the embedded notification module; banking-app publishes events to Kafka, notification-service consumes them.
Consequences: transfers stay fast and independent of SMTP; notifications are eventually consistent; two services, two databases, one more piece of infrastructure (Kafka).

ADR-003 — Double-entry ledger alongside transactions  Accepted

Context: a single transactions row cannot express per-account movements cleanly, and audits need a balance trail.
Decision: every transaction writes LedgerEntry rows (DEBIT/CREDIT) with balance_after_entry. A transfer writes exactly one DEBIT and one CREDIT of equal amount.
Consequences: statement generation and reconciliation become trivial; extra writes per transaction.

ADR-004 — Child references parent, no bidirectional collections  Accepted

Context: @OneToMany collections invite N+1 queries and accidental cascade deletes.
Decision: children hold @ManyToOne(fetch = LAZY) to the parent (Emi → Loan, LedgerEntry → Transaction, Account → Customer); parents stay thin; children are fetched with repository queries.
Consequences: predictable SQL; slightly more repository methods.

ADR-005 — Break service cycles by depending on repositories  Accepted

Context: LoanService needs EmiService (generate schedule) and EMI payment must close the loan.
Decision: EmiServiceImpl depends on LoanRepository, never on LoanService.
Consequences: no circular bean dependency; loan status rules for closing live in the EMI service.

ADR-006 — Stateless JWT authentication  Accepted

Decision: HS256-signed JWT, subject = e-mail, 24 h expiry; SessionCreationPolicy.STATELESS; CSRF disabled (no cookies).
Consequences: scales horizontally; tokens cannot be revoked before expiry until refresh tokens / a deny-list are added.

ADR-007 — Money as BigDecimal / DECIMAL(18,2)  Accepted

Decision: all amounts are BigDecimal in Java and DECIMAL(18,2) in MySQL. The EMI formula uses double only for (1+r)^n and rounds immediately with HALF_UP.
Consequences: no floating-point drift in stored balances.

ADR-008 — Optimistic locking on Account  Accepted

Decision: @Version column on accounts. Concurrent writers to the same account cause an ObjectOptimisticLockingFailureException instead of a lost update.
Consequences: correct under concurrency; clients may need to retry (currently surfaces as HTTP 500 — mapping to 409 is PLANNED).

ADR-009 — Keep MySQL (not PostgreSQL)  Accepted

Decision: the roadmap mentioned PostgreSQL for later days; the project has used MySQL from day 1, so it stays on MySQL 8.
Consequences: no migration risk; Flyway uses flyway-mysql.

ADR-010 — Schema owned by Flyway in production  Proposed

Decision: capture the Hibernate-generated schema as V1__baseline.sql, add indexes in V2__indexes.sql, and run prod with ddl-auto=validate.
Consequences: reproducible schema; every change requires a migration file.

ADR-011 — Cache-aside with full eviction for accounts  Proposed

Decision: @Cacheable("accounts") on reads by id and by number; @CacheEvict(allEntries = true) on every write (account updates and deposit / withdraw / transfer), 10-minute TTL.
Consequences: never serves a stale balance as long as every write path evicts; TTL bounds the damage of a missed eviction.

ADR-012 — Two-layer rate limiting (Nginx + app filter)  Proposed

Decision: Nginx limit_req per IP at the edge; RateLimitFilter per user / endpoint in the app (Bucket4j in-memory first, Redis Lua fixed-window for multi-instance).
Consequences: brute-force protection on /auth/login; 429 responses with Retry-After.
