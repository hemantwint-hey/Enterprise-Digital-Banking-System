1. Core Concepts: Why Unbounded List<T> Endpoints Fail at Scale

Today, every list endpoint in our codebase (TransactionController.getTransactionHistory, AuditController.getAllAuditLogs, LedgerController.getLedgerByAccount, CustomerController.getAllCustomers, etc.) returns a full List<T>. With 10 rows in development it feels fast; with 500,000 ledger entries in production, a single GET /history loads half a million entities into JVM heap, triggers GC pauses, saturates network bandwidth, and crashes clients.

Client: GET /api/v1/transactions/account/1/history?page=0&size=20 │ ▼ Spring Web HandlerMethodArgumentResolver (clamps size <= max-page-size=100) Pageable(page=0, size=20) │ ├─► Query 1 (Data Slice): SELECT ... FROM transactions WHERE ... LIMIT 20 OFFSET 0 │ (Uses Day 70 B-Tree Index idx_tx_source_created!) ├─► Query 2 (Count Total): SELECT COUNT(t.id) FROM transactions WHERE ... │ (Skipped automatically if slice size < limit or Slice<T> used) ▼ Page<Transaction>.map(transactionMapper::toSummaryResponse) ──► PagedResponse<T> JSON

Page<T> vs Slice<T> vs List<T>

  • List<T>: No SQL LIMIT, dangerous for unbounded tables.
  • Page<T>: Executes 2 SQL queries (data slice + COUNT(*)). Best for admin tables needing total pages & jump-to-page UI.
  • Slice<T>: Requests size + 1 rows to set hasNext with NO COUNT(*) query! Best for infinite mobile scroll feeds.

Why Custom PagedResponse<T> Over Raw Page<T>?

  • Spring Data 4 warns when serializing raw PageImpl directly to JSON: internal structure is unstable across versions.
  • RedisCacheConfig cannot safely serialize/deserialize raw PageImpl (used by AccountServiceImpl!).
  • A lean PagedResponse<T> exposes an explicit, clean JSON API contract & Swagger schema.

src/main/java/.../common/dto/PagedResponse.java NEW 
package org.example.enterprisedigitalbankingsystem.common.dto;

import lombok.*;
import org.springframework.data.domain.Page;
import java.io.Serializable;
import java.util.List;

@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder
public class PagedResponse<T> implements Serializable {

    private static final long serialVersionUID = 1L;

    private List<T> content;
    private int page;
    private int size;
    private long totalElements;
    private int totalPages;
    private boolean first;
    private boolean last;
    private boolean empty;

    public static <T> PagedResponse<T> from(Page<T> springPage) {
        return PagedResponse.<T>builder()
                .content(springPage.getContent())
                .page(springPage.getNumber())
                .size(springPage.getSize())
                .totalElements(springPage.getTotalElements())
                .totalPages(springPage.getTotalPages())
                .first(springPage.isFirst())
                .last(springPage.isLast())
                .empty(springPage.isEmpty())
                .build();
    }
}

// TransactionServiceImpl.java
@Override
@Transactional(readOnly = true)
public PagedResponse<TransactionSummaryResponse> getTransactionHistory(Long accountId, Pageable pageable) {
    if (!accountRepository.existsById(accountId)) {
        throw new ResourceNotFoundException("Account not found with id: " + accountId);
    }
    Page<TransactionSummaryResponse> mapped = transactionRepository
            .findBySourceAccountIdOrDestinationAccountId(accountId, accountId, pageable)
            .map(transactionMapper::toSummaryResponse);
    return PagedResponse.from(mapped);
}

// TransactionController.java
@GetMapping("/account/{accountId}/history")
public ResponseEntity<PagedResponse<TransactionSummaryResponse>> getTransactionHistory(
        @PathVariable @Positive Long accountId,
        @PageableDefault(size = 20, sort = "createdAt", direction = Sort.Direction.DESC) Pageable pageable) {
    return ResponseEntity.ok(transactionService.getTransactionHistory(accountId, pageable));
}

6. Verification & Performance Notes

  • Verify Pagination Metadata: curl -H "Authorization: Bearer $TOKEN" "http://localhost:8080/api/v1/transactions/account/1/history?page=0&size=5" — verify response contains content (5 items), totalElements, totalPages, first: true, last.
  • Verify DoS Clamp: Request ?size=5000 and verify returned size is clamped strictly to 100!
  • Interview Deep Dive — Offset vs Keyset/Cursor Pagination: Standard OFFSET 100000 still requires MySQL to scan and discard 100,000 index entries. At multi-million row scale (e.g., bank reconciliation), replace deep offsets with Keyset/Cursor pagination (WHERE created_at < :cursor ORDER BY created_at DESC LIMIT 20), which achieves constant O(log N) latency on any page depth using Day 70's composite index!
